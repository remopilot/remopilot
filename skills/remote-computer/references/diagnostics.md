# Machine and gateway diagnostics

1. Use machine_list to verify the specified account machine, online state, and heartbeat. When offline, previously reported capabilities are not current evidence. desktopEnabled=true does not prove healthy adapters or OS authorization.
2. Use the existing target binding or an explicit scope="machine" binding for gateway evidence. Machine bindings need no project directory. Diagnose project access failures through the original project binding.
3. Discover actual gateway_profile and gateway_diagnose inputs with names + detail="input". Inspect profile only for connectivity or capability discrepancies. Interpret diagnose by the actual failing layer; matching versions alone do not prove health.
4. Query get_usage_stats/get_recent_tool_calls only for call anomalies, narrowing the window and output as needed. Do not poll durable task progress through statistics; use manage_run/manage_call on the original binding. Execution statistics omit relay entrypoints such as machine_list/workspace_open. With authorization to diagnose the relay host, `remopilot state --state <actual-relay-state-directory> --action calls` reads recent entry summaries; correlate auditId/requestId with original records. Missing or old records do not prove no call occurred. Read complete execution receipts from the machine journal with workspace_history(source="agent"), paginated by authorized project and original call ID. Current cloud source="relay" supplies routing indices only and ignores typed-ID detail selectors; local sources retain their respective journal functions. HTTP finish is not host acknowledgement.
5. Only if that evidence is insufficient, discover execution tools and run necessary system commands. Machine bindings omit cwd/workDir/pathMode. The service uses an independent managed directory; commands still run as the agent's OS user, not in a Shell sandbox.
6. For unavailable desktop adapters, report actual evidence about allowDesktop, allowCommands, platform, adapter, or OS permissions. Use remote-app for observation/interaction; diagnostics should not duplicate click workflows, expand permissions, or install replacement remote control automatically. `DESKTOP_DISABLED` means the machine capability is off, not that the visible TCC rows failed. The owner can enable it from the App's fourth “桌面控制” row (or local `app-control --action enable-desktop`). Missing `app_access` with desktop enabled usually means the executable catalog is stale; `app_run`/`app_permissions` still require commands, which the owner can enable from the fifth “命令执行” row. Do not invoke these machine mutations on the user's behalf without explicit authorization.

See [platform-access.md](../../remote-workspace/references/platform-access.md) for macOS directory probes and [host-recovery.md](../../remote-workspace/references/host-recovery.md) for host chat recovery. Clean up only helpers started for this task that are no longer needed; preserve existing user processes and services.

The gateway exposes RemoPilot built-in tools and owned native App control. It does not discover or proxy external terminal/file MCP servers, resources or prompts. Files and commands use the access policy configured for each binding. Do not restore an external MCP adapter or broaden directory permissions to repair a missing tool. Existing historical metadata and original run/call recovery remain available.

After macOS permission changes, recheck and retry the original feature before requesting a restart. Foreground and background fresh-probe results can expose a mismatch but do not establish that restarting will fix it. The Mac App offers guarded restart, update and full quit for its recorded connection. Check any failed or uncertain lifecycle operation by its saved operationId; do not force-stop the agent or change keys to bypass its drain checks. Closing the permission window alone leaves the background running.
