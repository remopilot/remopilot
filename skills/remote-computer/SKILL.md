# Machine diagnostics and commands

Use the [core calling contract](../remote-workspace/references/calls.md) once per task and target version. Confirm the requested machine with `machine_list`; inspect online state, agentVersion, command permission and machineRoutingSupported. Offline metadata is historical evidence.

Reuse the explicit task binding, or create `workspace_bind(scope="machine", machineId, requestKey)` when no project is needed. A machine binding is routing, not a shell sandbox. It does not accept project paths, cwd, pathMode or workDir. Commands start in the machine's configured user work directory and run with its OS user's permissions. Do not substitute caller-local commands or bind an arbitrary project to bypass missing machine support.

For a known tool, request `workspace_tools(detail="input", names=[...])` directly. Use gateway_profile for capabilities and gateway_diagnose for health; use get_usage_stats or get_recent_tool_calls only for statistics or call anomalies, not task progress. Interpret the current schema and installed toolchain before choosing commands. See [diagnostics.md](references/diagnostics.md) when diagnosing a failure.

For changes, keep the target plan under the [planning contract](../remote-workspace/references/planning.md). Declare machine coordination for installation, service registration or machine-wide changes; declare shared resources for bounded conflicts. Starting a long command in detached mode changes observation, not its execution deadline. Retain original IDs and verify terminal state and effects before reporting completion.

Check desktopSessionAvailable only when GUI work is relevant. If absent, inspect desktop diagnostics; unknown is not unavailable, and enabled configuration is not proof of a usable screen. When unavailable, continue independent files/commands and report the requested GUI portion as blocked. Do not start display services or enable permissions automatically. Use [remote-app](../remote-app/SKILL.md) for apps, [remote-mobile](../remote-mobile/SKILL.md) for Simulator projects, and [remote-tasks](../remote-tasks/SKILL.md) for execution recovery.

A user-authorized update needs machine coordination. Download, installation, service activation and background access are distinct results; inspect their evidence separately. An old running generation can remain for its original tasks. Do not retire it, delete state or replay an execution to resolve a version difference. For a requested browser desktop connection, inspect the advertised capability and read [remote-desktop.md](../remote-app/references/remote-desktop.md).

Mac App lifecycle commands use only the recorded managed cloud connection: `remopilot app-control --action status|restart|quit|enable-desktop|enable-commands`. Status checks a fresh helper under the background identity, reports command and desktop capabilities separately from macOS grants, and does not prove existing App sessions have applied a grant. Restart/quit/enable-desktop/enable-commands require explicit user authorization, machine coordination, and a nonce-bound idle intake pause; active tasks, owned App sessions, pending receipts, other live generations of that connection, or incomplete evidence block the action. Enable-desktop writes `allowDesktop` only after the original PID exit is confirmed, then starts the same generation so missing TCC permissions can be requested; enable-commands writes `allowCommands` under the same checks and grants shell execution as the current OS user, with directory roots not acting as a sandbox. They are the owner actions exposed by the App's fourth and fifth rows and are never automatic permission grants. Quit disables login startup for that connection while preserving pairing/data and other connections. Use the local App lifecycle entry; invoking a stop from a job owned by the same agent remains busy. Never bypass a refusal or replay an uncertain stop/start; retain its local operationId and receipt.
