# Observe and interact with mobile devices

Use the [core calling contract](../cloud-connection/references/calls.md) once per task and target version, and the [planning contract](../cloud-connection/references/planning.md) when the host determines a durable plan is needed. Existing execution recovery need not wait for reloading skills. Use computer-development for source edits. A simulator on the caller's computer is not the simulator on a different bound machine.

1. Confirm the requested machine, project or machine binding, OS, device and app. Read `task_query(catalog)` with `detail=summary` and `names=["device_run"]` for that binding and inspect `mobilePreflight` before planning mobile work; this selector requests the mobile observation even for a machine binding that does not expose `device_run`. It is an on-demand, asynchronous, timestamped observation made by the machine agent, not the client's desktop process. It reports iOS simulator IDs, the selected and highest detected installed Xcode versions, and whether Android Studio, its emulator tool and a configured virtual device were found. Studio and Xcode app discovery cover standard Applications folders only; the highest detected local Xcode version is not necessarily Apple's latest release. `checking`, `unknown`, `blocked`, `stale`, a missing field, and `attention` are not verified availability; report the actual reasons. If checking or refreshing, wait for the ongoing bounded observation and reread the same target catalog rather than starting repeated probes. `prerequisites_observed` still leaves authorization, the selected target and actual requested interaction unverified. An older agent may not report this field. Discover `run_command`, `manage_run` and `read_artifact` through that binding's actual catalog; command access is required. Use the individual operation tools on hosted cloud, or the local relay `workspace_call` described in the core contract. The execution machine's tools and permissions, not this Skill or the caller's installed tools, determine availability.
2. For iOS Simulator, use the target Mac's Apple Xcode MCP through the explicit `remopilot mobile-xcode` client and [Apple reference](references/apple-devicehub-mcp.md). Read its live catalog and exact input schema; select the real Xcode workspace and an exact simulator UDID in an available iOS runtime of the selected Xcode. DeviceInteraction sessions are checked against that current inventory and Xcode's returned device. Inventory checks can take up to 45 seconds; observe the original run rather than retrying a slow response. The Mac client's **专项连接 → Xcode 模拟器** row can request agent and folder access for a project chosen by the owner; only an actual background call can verify its access. `remopilot mobile-status` and the client show local tool versions, iOS inventory and configured Android AVDs; ADB runtime status comes only from an already-running local ADB server. These observations do not prove device interaction, Xcode project authorization or background readiness. The client viewer controls affect its local display and wake entry points only, not shell or existing tasks. Do not assume a particular action or physical iPhone is supported.
3. For Android simulators, use Google Android CLI and ADB on the selected computer via the existing `run_command` MCP tool; follow the [Android reference](references/android-cli.md). On macOS, `remopilot mobile-android --action gesture` can send a multi-touch gesture to a matching emulator with a token-authenticated local gRPC endpoint. Select an exact device serial for each command. The Google plugin is an Android CLI Skill, not an Android MCP server. A connected physical device is a separate requested target and requires its actual connection and authorization.
4. Use a fresh device screenshot or UI hierarchy, identify the target within that same device, perform one requested action, then observe again and verify the effect. Capture and inspect actual images through `read_artifact`; a remote path alone is not a displayed image. Never claim delivery, interaction or backend success from a command exit alone. Coordinate all calls affecting the same device using the same `device:<lowercase device ID>` resource. Retain original binding, request and run IDs; uncertain actions must be recovered or observed, never automatically repeated.
5. `device_run` remains the separate managed iOS build/install/launch/screenshot/log workflow in [ios-simulator.md](references/ios-simulator.md); it does not itself provide simulator interaction, Android or physical-iPhone support. For other devices and failure diagnosis see [devices-and-failures.md](references/devices-and-failures.md).

Keep the user's existing devices and instances. Clean up only task-created instances after their original operations are confirmed ended, capturing requested evidence first. If closure or input is uncertain, preserve the instance and recovery evidence. Do not automatically install SDKs, enable permissions, approve an Xcode prompt, or switch devices to work around a failure. A screenshot may contain private data; access is limited to the user's requested task.
