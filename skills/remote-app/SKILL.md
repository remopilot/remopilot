# Operate an owned App instance

Use the [core calling contract](../remote-workspace/references/calls.md) once per task and target version. Reuse the explicit machine/binding/session; for app-only work, use a machine binding. Native App control requires macOS 14 or later, or Windows with the Windows adapter, plus a usable desktop session, the installed adapter and (on macOS) the relevant permissions. Linux and command support on any platform do not establish App control. On Windows the same tools apply through UI Automation, with the differences listed in step 7 and in [app-entities.md](references/app-entities.md).

Check desktopSessionAvailable or desktop diagnostics before GUI work. When unavailable, report the GUI limit and continue independent noninteractive work. app_capabilities checks current permission and entity ownership support without prompting. Accessibility supports AX reads/input; images additionally need Screen Recording. Missing image permission does not block AX-only work. Use app_permissions only for requested authorization and let the user make system consent decisions. See [app-troubleshooting.md](references/app-troubleshooting.md).

Remote catalog policy: app_access requires desktop control only. app_run and app_permissions additionally require command execution because they run a bounded workflow or request machine-level authorization. If app_access is missing while desktop is enabled and the adapter is available, refresh the machine catalog or update an older agent; do not broaden permissions or switch machines.

1. Find the real absolute .app path (macOS) or .exe path (Windows) with app_installed (read-only, optional name filter), then open it with app_access(open), retaining entityId. It creates an exclusive background process; do not borrow the user's original instance or another caller's entity/window. For a bounded workflow, app_run can create, operate and clean up its instance.
2. Keep isolation=strict when the app supports an independent profile. isolation=process shares app data and requires the user's acceptance. Neither is an OS sandbox. Coordinate shared documents, caches and outputs; unsupported isolation is a real limitation.
3. Observe the owned entity with tree/elements, or image/both when visual evidence is needed. For multiple windows, verify a live controllable windowId and observe that exact window. See [targeted-observation.md](references/targeted-observation.md).
4. Act with a fresh snapshot and elementId from the same entity. press and string setValue/type are supported; clickAt, drag and scroll post pointer events with window-relative point coordinates, and menu presses an AX menu item by title path (Quit items are refused); key and typeText post background key or Unicode events to the owned PID for custom canvases that expose no settable AX text. Enter text without touching the user's front window whenever possible: first target a settable text field (observe lists isValueSettable) with setValue or type, or pass its elementId to typeText, which then appends through AXValue (via=setValue) and needs no focus. For a background App, typeText inserts at the focused element through accessibility (via=axSelectedText); if that is unavailable, pass clipboard=true to paste through the clipboard (restored afterwards; a selected-but-not-edited shape receives it as new content) or, for canvas Apps such as slides, borrowFocus=true to take the front for about a quarter second and hand it back to the App the user was in. Password fields are never typed into. Real keystrokes (plain keys such as Tab or Return) reach only a frontmost App: call activate first and confirm frontmost=true, otherwise the request is refused with APP_NOT_FRONTMOST, nothing is sent, and the refusal lists backgroundTextTargets to try first; command/control shortcuts and menu presses work in the background. activate is the only focus-changing action: it brings the owned App to the front and takes focus from the user's current window, so use it only after setValue/type and background key produced no effect, then observe again (activation changes the window context, so earlier snapshots become invalid), and expect the user's physical keyboard to reach that App while it is frontmost. cmd+Q and force-quit shortcuts are refused; cmd+W, cmd+delete and similar shortcuts are not, so close, save, send and delete only on the user's explicit request. Every observe result lists overlays, windows of other processes drawn above the target (system prompts, permission dialogs, banners). Overlays with blocking=true (alerts, panels, banners; ordinary windows are only listed) refuse pointer actions covered by them with FOREIGN_OVERLAY_COVERS_TARGET: report the overlay to the user, never click through it, and never operate another process window. Sheets and dialogs of the owned App itself appear as its own windows or AX elements. Every observe also returns dialogs (sheets and dialogs of the owned App with texts and button titles such as Save, Do not save, Cancel) and otherWindows, so never watch a single window and ignore prompts: answer a listed dialog with app_access(answerDialog, button, optional dialogIndex), only as the user asked, and read dialogs again afterwards. close and status also list a pending prompt and keep the entity controllable until it is answered. layout (placement left-half, right-half, center or full) moves the observed window into a region of the main display; it is a convenience layout, not isolation, and macOS offers no supported API to create or switch Spaces. Other windows of non-system processes are reported as overlays; small prompts of the same vendor or a child process of the App, or ones that cover it (a vendor updater, for example), are read as foreignDialogs, even before the App has a window (a failed observe still returns dialogs and foreignDialogs) with texts and button titles, and may be answered with answerDialog and foreignWindowId only when the user asked (a window close button is offered as [Close window]; never choose Retry, Install or Update on your own). answerDialog rescans afterwards and returns stillPresent: some system-owned prompts cannot be closed from outside, so when stillPresent=true read it, then leave it, ask the user or activate the App; do not repeat the press. open launches without activation and a short focus guard hands the front back to the App the user was in if the launched App or its updater takes it. System, credential and password windows are never read or operated: ask the user with app_access(requestHelp, message, optional title and placement): it posts a local notification, raises the window inside its own App and moves it to the placement region (default untouched) without activating anything, so the user decides when to switch. Use it for passwords, payments, permission prompts and any choice that must stay with the user. While the helper acts, a click-through purple AI cursor glides to the operated point (set REMOPILOT_AI_CURSOR=0 to hide it); it is only a display overlay and never moves the real pointer. Input invalidates old snapshots. Entity run cannot override its target. Public tools do not provide coordinate input.
5. For situational awareness outside owned windows, desktop_view returns one read-only main-display screenshot. It is exposed only after the machine owner runs configure --screen-view enable (requires desktop control; macOS also needs Screen Recording, Windows needs an unlocked interactive desktop), shows every visible App, and gives image evidence only: no elementId, snapshot or coordinates, so it can never be an action target. Prefer app_access(observe) for owned windows; do not capture passwords, private messages or other sensitive content unless the user asked. If desktop_view is absent from the catalog, tell the user how to enable it; do not substitute app_run or commands.
6. Verify business effects after input. AXPress delivery does not prove success. For uncertain effects, recover the original operationId with app_access(recover) or app_operation and the original gateway call/run; do not create a new instance to replay input.
7. Windows differences. Roles keep the AX names (AXButton, AXTextField) and press invokes, toggles, selects or expands through the first UI Automation pattern the element supports; the result's via names it. Windows needs no permission grant for UI Automation or window capture, but an App running as administrator is refused with ELEVATED_TARGET_UNSUPPORTED and UAC or secure-desktop prompts can only be answered by the user. key, clickAt, drag and scroll are posted as window messages and reported delivered, never confirmed: posted modifier keys are invisible to most controls, so ctrl+a/c/x/v/z become edit messages and other shortcuts are unreliable; prefer press, menu or setValue. Use ctrl or alt (option is an alias for alt); cmd and the Windows key are refused, and alt+f4 and ctrl+q are blocked. typeText tries accessibility at the focused control, then clipboard=true, then borrowFocus=true, then posted characters (classic edit controls or a frontmost App), otherwise APP_NOT_FRONTMOST with nothing sent. Before press or setValue a click-through AI cursor glides to the element, as on macOS; it is purely visual, never moves the real pointer and is skipped for windows on another virtual desktop. desktop_view is available after the same separate opt-in and returns physical pixels (display.unit is pixels, the cursor is drawn, a locked or secure desktop is refused); foreignDialogs (prompts of other processes) are still not read. If the machine owner set `configure --app-desktop virtual`, open puts every window of the App on a dedicated virtual desktop named RemoPilot (optionally RemoPilot · desktopLabel; pass a short task name as desktopLabel on open, entities with the same label share a desktop) so the user's own desktop is untouched. The entity's desktop field says mode=virtual, or mode=current with fallback when the desktop could not be used (Windows 11 24H2 or later is required). On that desktop activate and borrowFocus return ACTIVATE_WOULD_SWITCH_DESKTOP instead of pulling the user away, and requestHelp flashes the taskbar button, raises the window and names the desktop to switch to (Win+Tab). Never switch the user's desktop yourself.

Normally release access and gracefully close the instance created for the task. Use retain=true only when the user requests retention. Saving, sending and deleting need the corresponding requested scope. For retained/close_pending/execution_uncertain, preserve entityId, operationId/callId, original binding and blockers; do not force-kill or remove locks.

Read [app-entities.md](references/app-entities.md) for not_ready/launch_unconfirmed, resolveLaunch, ownership and cleanup. The separate administrator browser desktop workflow is described in [remote-desktop.md](references/remote-desktop.md); it does not expand MCP App permissions.
