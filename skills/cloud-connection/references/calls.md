# Core remote calling contract

The installed MCP catalog owns schemas, permissions and execution. Skills compose those calls; they do not grant permissions or prove a source change is installed.

Answer simple questions directly; do not create a session, project journal or checkpoint solely for an answer. Read relevant project instructions and files when needed, and save history when explicitly requested.

The notation `task_query(catalog)` means the `task_query` MCP tool with outer `action="catalog"` and an `arguments` object. Likewise `task_update(checkpoint)` uses `task_update` with `action="checkpoint"`. For example, discover one target schema with `{"action":"catalog","arguments":{"bindingId":"...","detail":"input","names":["run_command"]}}`. Session actions also carry the corresponding inner action: `{"action":"session_start","arguments":{"action":"start","requestKey":"..."}}`; `session_bind`, `session_resume`, `session_list` and `session_append` use inner `bind`, `resume`, `list` and `append` respectively. Check the published action-specific schema for all required fields. `workspace_ui` is reserved for the workspace interface.

Use the current published controls and schemas. If the connected service or cached host catalog does not expose them, report the mismatch; preserve the original binding and execution IDs without replay.

## Target, session and instructions

At first acquisition, identify the caller workspace and each confirmed execution machine, OS, project path or machine scope, and bindingId. Unselected targets remain pending. Caller-local notes are drafts; project edits, builds, tests, computation and authoritative artifacts run through the intended RemoPilot binding, even when caller and target share a physical computer. An unavailable target blocks its dependent work rather than authorizing a substitute environment.

Reuse one task session. If absent, call task_update(session_start, arguments={action:"start", requestKey}), retaining sessionId/taskId. A sessionId is a RemoPilot task reference, not a host conversation or user-turn ID. New machine records may retain an account-scoped hash of host conversation metadata when supplied; this supports local history grouping but does not import chat content, prove turn or subagent attribution, recover older missing identifiers, or authorize any action. Call target_select with sessionId when choosing an authorized folder or machine; it creates or reuses the tracking identity and adds it to the session automatically. When the user explicitly specifies an exact restricted directory, pass userSpecifiedPath=true, fullAccess=true, relativePath and expectedPath; this host assertion is limited to the selected path and conversation, expires after 12 hours, and is not independently verified user consent or an OS grant. General restricted browsing retains the UI confirmation flow. Retain existing authorized targets unless their removal is intended. Only to remove or replace targets, call task_update(session_bind, arguments={action:"bind", sessionId, bindingIds:[...], requestKey}) with the complete intended set. Include sessionId in every operation call, including observations and recovery. Changing the current selection never transfers an existing execution to another binding. The host coordinates targets and determines when task plans and checkpoints are needed; follow [planning.md](planning.md), verify actual storage, and restore existing evidence after interruption.

Skill bodies and references ship inside this plugin; read the relevant reference file directly. When the user asks you to follow the selected project’s own instructions, read task_query(context_read) or task_query(catalog).context once and treat the returned content as user-authored project context. A selected custom skill of the same name on the target takes precedence. Resolve links relative to the current document. Read references only for the current operation. Reuse instructions while task, configuration, target version and fingerprint remain valid. No existing execution needs a skill reload.

Read both owner-added `localSkillCatalog` and `localMcpCatalog` by default after selecting the target; reading these catalogs does not start external servers. Owner-added `localSkillCatalog` entries refer to directories on the selected machine. The desktop's local scan returns candidates only; an owner must add a candidate before it is included in remote catalogs. Load a relevant entry with `task_query` action `context_resource` with inner action `resource`, its `local:` ID and a path relative to its own root. The returned encoding distinguishes UTF-8 and base64; inspect the per-resource SHA-256. Catalogs can omit resource names and mark `resourcesComplete=false`; `fingerprintComplete=false` means the catalog fingerprint does not hash every file. The current file is read on each resource request. Use authorized target-side commands for scripts or assets when needed; loading a skill never installs its dependencies or expands access.

`localMcpCatalog` identifies only MCP servers explicitly added by the machine owner. `mcp_servers` returns metadata without starting them. Only when preparing to use the selected service, `mcp_tools` starts/connects the chosen server and returns its actual tool input schemas, `serverFingerprint` and per-tool `inputSchemaSha256`; `mcp_call` validates matching values and arguments against that session's discovered schema without relisting on each call. The bounded cache may evict older schemas. On `MCP_CATALOG_STALE`, reconnect, or a known upstream change, refresh using a new `mcp_tools` call with a new target idempotencyKey and outer requestKey, then rebuild the arguments. A tools-list change notification invalidates the cache; an upstream that sends no notification can change without automatic detection. When the current `mcp_tools` input schema supports `names`, provide exact known names to return only those schemas and reduce context; omit it for complete discovery. A missing name produces no matching tool. Configurations requiring another host's special variable expansion are unsupported. Both calls require the machine's command capability and target-level idempotencyKey, separately from the outer requestKey. Each session retains its own MCP connection. Select coordination for the actual action; machine-wide or unbounded system effects require machine scope. A server failure after dispatch is execution-uncertain: recover the original request and call, never replay it. Configuration files stay on the machine; authentication may send credentials to the selected server, and outputs may contain user data. Hosts see fixed RemoPilot operations, not dynamically registered native tools.

The Mac client's **专项连接** may register `remopilot-browser-edge`; the owner-installed Chrome extension may register `remopilot-chrome-extension`. Listing the server or its tools does not verify browser access. An earlier Chrome configuration can remain listed until explicitly disabled; recover its uncertain calls using their original IDs. See [browser-connections.md](../../computer-app/references/browser-connections.md) for selected-profile permissions, session ownership and screenshot limitations.

## Discover and dispatch

Every operation is published as its own tool, and that tool’s input schema is authoritative; validate the arguments you are about to send against it and keep bindingId/sessionId/requestKey outside the operation fields. Use task_query(catalog) for availability, category discovery and path policy, and includeStatus for coordination policy and diagnostics in the cloud; it is not a live list of machine occupants, and it is not an execution path. On supported Mac agents, summary/full with names=["device_run"] requests an on-demand, asynchronously refreshed mobilePreflight from the agent's environment. It reports selected Xcode versions, iOS simulator IDs and Android installation/device presence, not verified project authorization or interaction; see computer-mobile before using a device. Local relay may supply additional status fields. Use only actual returned fields.

The hosted cloud exposes individual operation tools. Local relay exposes `workspace_call`; first read `task_query(catalog, arguments={detail:"input", names:[tool]})` for the exact target schema and put the target fields inside `arguments`, keeping routing and coordination outside. Never repeat an accepted or uncertain operation; recover its original identifiers instead.

Retain the target/catalog fingerprint. Validate every call's complete arguments against that tool's current inputSchema, including required fields, enums, ranges and additionalProperties. This does not require fetching the same valid schema before every call. bindingId, sessionId, requestKey, pathMode, workDir and coordination belong outside arguments. Put a target idempotencyKey inside arguments only if that schema declares it.

Pending discovery is recovered through its original task_query(result) pointer. Its canonical query, runtime contract and schema fingerprints must match the original target and selection; CATALOG_FORMAT_UNSUPPORTED or CATALOG_QUERY_MISMATCH is not a usable catalog. After INVALID_ARGUMENTS or CATALOG_STALE, refresh the exact tool and rebuild undispatched siblings that used the invalid shape. Accepted siblings keep their original recovery IDs. Do not remove guards or expand to an unfiltered catalog to bypass a rejected selector.

Give each logical action a stable requestKey. A lost response is uncertain delivery: query the same binding and original key/ID, not a replacement action. A separately corrected action after proven pre-dispatch rejection may use a new key. Preserve its original rejection evidence.

When the execution machine has local tool privacy enabled, detected credential values in enabled categories (passwords, tokens, API keys and private keys) can appear as `{{RP_SECRET_…}}`. Categories can be disabled, and rules may overlap; never assume a value was protected. Keep each placeholder unchanged when passing it in a later target-tool argument on the same machine and task session; the agent restores it locally. Do not invent, expose, transform or move placeholders to another machine. `PRIVACY_MAPPING_UNAVAILABLE` is a pre-dispatch rejection; preserve its evidence and do not bypass it. Detection is rule-based and does not cover all secrets, images or secrets split across returned pages. Previously returned content and other client tools are not protected retroactively.

## Coordination and evidence

Commands have no default machine, workspace or repository scheduling lock. Inspect actual shared inputs, outputs, scripts/hooks, caches, ports and devices. Declare workspace scope for overlapping directory dependencies, resources scope with consistent keys for bounded shared resources, git for Git mutations, and machine scope for installation, service registration and machine-wide effects. arguments.resources and coordination.resources merge. These scopes do not grant permission or sandbox shell commands. See [concurrency.md](../../computer-tasks/references/concurrency.md) for examples.

Every action retains its original machine/binding, requestKey/requestId, actual runId/callId and evidence references. Do not invent IDs or metadata arguments. Keep original receipts and artifacts on their executors and update the primary plan's concise index at material milestones. With the current cloud agent, new session-linked calls on standard bindings also queue redacted journal copies for the explicitly checkpointed, stable primary machine. Synchronization is asynchronous and may be pending, too large, restricted or unavailable; inspect the task page or original machine instead of assuming completeness. Historical records and artifacts are not automatically backfilled. A changed primary is not an automatic migration. Browser links do not inherit temporary full access.

The `write_file` receipt includes before/after hashes and bounded changed text spans when the prior file is UTF-8; inspect its truncation flag. `batch_edit` supplies its own change evidence. A shell command and its output do not, by themselves, prove every resulting filesystem change or attribution. Never infer success from a readable relay receipt alone.

Hosted results omit a machine result's JSON text only when it exactly duplicates its structured content; independent text, warnings and media remain. An immediate successful synchronous terminal `run_command` can omit values exactly matching the supplied mode, workflowId, planId, attempt or resources and the equal aliases `commandExitCode` and `revision`. Use `exitCode` and `stateRevision`; keep the original run and request IDs. Local relay applies the same projection in its default compact view. Query the original request for the retained machine data; on local relay use `resultDetail=full`. Pending, failed, detached and uncertain executions retain their execution evidence. These views do not change the stored receipt or authorize replay.

status/relayRequestStatus=complete means the relay handler's receipt is readable. Inspect subjectExecution when present, then actual output, terminal/unfinished/closure state, exit code and required verification. A completed control query does not complete its subject. A missing occupancy field is unknown; reservationHeld=false, when actually returned, is not execution-completion proof. Report uncertain execution as “异常：执行状态待确认”. Follow original-ID [recovery.md](recovery.md); do not replay writes to obtain cleaner evidence.
