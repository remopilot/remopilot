# Apple Xcode MCP and Device Hub

Apple's Xcode MCP is an external server on the selected Mac. It is not dynamically merged into the RemoPilot gateway catalog. `remopilot mobile-xcode` is an explicit local MCP client invoked via the target's authorized `run_command`; `manage_run` observes that durable command and `read_artifact` delivers image files. Apple documents `xcrun mcpbridge` and requires the relevant Xcode configuration and a project open in Xcode: https://developer.apple.com/documentation/xcode/giving-external-agents-access-to-xcode .

1. Confirm the target Mac has a RemoPilot executable containing `mobile-xcode`, an appropriate Xcode, an available desktop/user session, an open relevant Xcode project, and any permission granted by the owner. The Mac client's **专项连接 → Xcode 模拟器** row lets the owner select a `.xcodeproj` or `.xcworkspace`; the bundled CLI uses `mobile-xcode --action authorize --file ABSOLUTE_PROJECT --folder PRIVATE_FOLDER` to ask Xcode to open it and potentially request agent and folder access. Xcode owns the prompts. An authorization request or approval for another executable does not prove that the background agent or selected project is permitted; verify the actual task. `xcrun --find mcpbridge` and `xcrun mcp-server status --format json` are diagnostics, not proof that the background agent is authorized or that device tools exist. Inventory checks have a 45-second limit; a slow or timed-out observation is not evidence that no simulator is installed. Never enable headless mode, grant permissions or approve prompts automatically. If authorization or a project is missing, report it and continue independent work.
2. Obtain a private existing absolute output folder under the same project binding. Invoke `remopilot mobile-xcode --action list --folder ABSOLUTE_FOLDER` via `run_command`. The command returns `resultPath` and tool names with `inputSchemaSha256`. Read that JSON with the binding's file tools, including descriptions and complete input schemas. Each invocation opens a new MCP connection; session-scoped upstream state may not survive. If Xcode supplies a session UUID required for subsequent connections, pass it as `--session UUID`; do not invent or confuse it with a RemoPilot session or assume this preserves all Xcode state.
3. Discover the actual Xcode workflow and identify the requested project/window and exact simulator UDID using returned evidence. `remopilot mobile-status` reports the selected Xcode's version, available iOS runtimes, and the simulator inventory's reported device states; it does not prove project authorization, action support or background readiness. The DeviceInteraction bridge requires an available iOS runtime and available simulator in the selected Xcode's current `simctl` inventory; there is no hard-coded iOS version ceiling. Tool names, required session setup, supported gestures, coordinates and screenshot shapes vary by Xcode version. If Xcode cannot establish the correct target, stop; do not operate another simulator or treat a desktop screenshot as device evidence. Apple's release notes describe simulator touch and screenshots, not blanket physical-device support: https://developer.apple.com/documentation/Xcode-Release-Notes/Xcode-27-release-notes .
4. Place a private UTF-8 JSON request in the same binding, with exactly `name`, `arguments` and the selected tool's `inputSchemaSha256` from the current list. Call `remopilot mobile-xcode --action call --file ABSOLUTE_REQUEST --folder ABSOLUTE_FOLDER` through `run_command`. Supply `--session` only for an actual Xcode MCP session UUID. The client reconnects, re-lists the catalog, checks the fingerprint and validates the complete arguments before dispatch. A stale or unsupported schema is a pre-dispatch failure; re-list rather than guessing arguments. Only use tools/actions authorized by the user's task. Request files and results remain on the target; never put passwords or credentials in them.
5. For `DeviceInteractionStartSession` and `DeviceInteractionStartWorkspaceSession`, supply the exact simulator UDID as `deviceIdentifier`, even if the live upstream schema makes it optional. The client checks Xcode's returned `deviceUUID` and `deviceIsSimulator` before accepting the session. If Xcode selects another device, the call returns `IOS_SIMULATOR_MISMATCH` and preserves the opaque handle for `DeviceInteractionEndSession`; do not send input. Its returned `interactionSessionKey` is a secret. The client stores it in private machine state and substitutes an opaque `xcode-device-session:...` handle in the result. Reuse that handle unchanged in `interactionSessionKey` or `interactSessionKey` on the same binding; do not copy the secret or invent a new session. Each synthesize/install call rechecks the selected simulator and its runtime; end-session remains available for cleanup even when the runtime is no longer available. Unknown DeviceInteraction tools are rejected until adapted. For `DeviceInteractionSynthesize`, use the live schema and current hierarchy for actions; inspect its resulting state and use `DeviceInteractionEndSession` to close only a session created by this task once all operations are confirmed ended. The client removes its local key only after a successful end response. If ending is uncertain, retain the handle and original evidence.
6. Retain the returned `runId`; a pending or lost response is recovered using that original run and binding. Read `resultPath` and inspect the upstream `response`, including `isError`. MCP image content is saved as private image files; for `DeviceInteractionSynthesize`, the client also copies Xcode's returned screenshot, hierarchy and log files into the output directory when readable, recording digests or individual copy errors. Read images with `read_artifact` on that binding and hierarchy with file tools. A remote path or unreadable file is not delivered evidence. An Xcode error, invalid response, timeout or connection loss after dispatch can leave the effect uncertain; inspect the device/current upstream evidence and never repeat an input automatically. A successful outer command or saved image does not prove the intended UI change.
7. Coordinate device-affecting commands with `coordination: {scope: "resources", resources: ["device:<lowercase-UDID>"]}` using the same actual device ID on all calls, and declare project/build resources where needed. Xcode session/window mappings are not an operating-system sandbox; verify the target on every meaningful context change. Do not stop the user's Xcode or close the user's simulator.

On Xcode 27.2, observed `DeviceInteractionSynthesize` examples include `t X Y` for a tap, `d X Y` for double tap, `t X Y 1.0` for a long press, `drag X1 Y1 X2 Y2 0.5 1.0` for a drag, `mt [X1 Y1, X2 Y2] 0.2 [X1_END Y1_END, X2_END Y2_END] 0.8` for a two-finger gesture, `orientation landscapeLeft` for rotation, `b h` for Home, `b p` for the power button, `t X1 Y1 f X2 Y2 0.3` for a swipe, and `sender keyboard kbd TEXT` for text in the focused field. These are version-specific examples, not a substitute for the current Xcode tool and device guidance. Take coordinates from the latest hierarchy, verify focus before typing, and keep text out of request files when it is sensitive. The returned screenshot and hierarchy can reflect different moments while typing or animations are in progress; after the action ends, capture again and verify the settled state rather than treating the first image as final.

When an upstream tool requires an MCP connection to remain alive or a session cannot be resumed across commands, report that limit; do not replace it with an invented session or repeat input. Device Hub UI support for connected Apple hardware does not establish MCP support for the same hardware. Xcode MCP and its permission prompts are owned by Apple; updating the RemoPilot source, plugin or agent does not install or authorize Xcode.
