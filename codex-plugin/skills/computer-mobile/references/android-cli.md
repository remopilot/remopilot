# Android CLI and ADB

Google's Android CLI and its official agent Skill are not an MCP server. Use the selected machine's installed `android` and `adb` through RemoPilot `run_command`; do not assume a CLI on the caller's computer is available remotely. Official references: https://developer.android.com/cli and https://developer.android.com/tools/agents/android-cli/commands/input .

1. Check `android --version`, `adb version` and `adb devices -l` on the target. `remopilot mobile-status` and the Mac client show tool versions, configured AVDs and emulator serials visible through an already-running local ADB server; they do not prove device interaction or background authorization. Unknown ADB state is not an empty device list. The multi-touch helper searches the configured Android SDK, the usual macOS SDK path and PATH for ADB, since launchd and a terminal can have different PATHs. Identify the exact requested emulator serial and its `device` state; never rely on automatic selection when a serial is available. A connected physical phone is a distinct target, requiring user intent plus its existing Android authorization. Do not auto-install SDKs, accept an authorization prompt, or change device settings.
2. On each call specify the serial explicitly. For example, `android layout --device SERIAL --pretty` reads the live hierarchy and `android screen capture --device SERIAL --output ABSOLUTE_PNG` captures the screen into a private folder under the same accessible binding. Register/read the PNG with `read_artifact` and inspect it; a path or successful capture command alone is not visual evidence. Use hierarchy plus image when a view is missing or ambiguous.
3. For an observed control, `android input --device SERIAL tap 'id=submit_button'` can tap by selector; `android input --device SERIAL swipe 'id=card' --dir=left` can swipe; `android input --device SERIAL text 'example' 'id=field'` replaces existing text in the selected field. Selectors and values here are examples, not target evidence. Verify exact installed CLI syntax with `--help`; prefer unique selectors and the default single-match behavior. Text input replaces existing content and its arguments can appear in OS process and command records: never send passwords or credentials this way.
4. If hierarchy-based input cannot address an element, `adb -s SERIAL shell input tap X Y` or `adb -s SERIAL shell input swipe X1 Y1 X2 Y2 DURATION_MS` uses current device-screen coordinates from a fresh image. Device dimensions, rotation, overlays and changed screens can invalidate them; re-observe before acting. Coordinate all device actions and captures with `coordination: {scope: "resources", resources: ["device:<lowercase-serial>"]}`. Do not infer success merely from the input command returning.
5. Use `run_command` with original binding, request key and target idempotency key; retain its `runId`. On pending or uncertain execution, observe that same run and actual device state before any further input. Do not repeat a tap, swipe or text entry to obtain a cleaner receipt. Keep screenshots and request data in private scratch and access only what the user requested. `device_run` does not implement these Android actions.

For an emulator, ADB also supports two successive `input tap` calls for a double tap, `input swipe X Y X Y 1000` for a long press, `input draganddrop X1 Y1 X2 Y2 1000` for a drag, and `input keyevent KEYCODE_VOLUME_UP` for a hardware key. Actual timing and supported key codes vary by Android and application; check the effect. For rotation of a disposable test emulator, `settings put system accelerometer_rotation 0` followed by `settings put system user_rotation 1` requests landscape; both commands must explicitly select the serial. Do not alter another device's rotation settings.

For multi-touch on macOS, if the running emulator advertises a **token-authenticated local gRPC endpoint**, create a private request file on the selected machine, using pixel coordinates from its current layout or image:

```json
{"serial":"emulator-5554","start":[{"x":240,"y":1113},{"x":480,"y":1113}],"end":[{"x":120,"y":1113},{"x":600,"y":1113}],"durationMs":720}
```

Call `remopilot mobile-android --action gesture --file ABSOLUTE_REQUEST_JSON` using `run_command` and the same `device:<lowercase-serial>` resource. `serial` must name an ADB emulator; `start` and `end` contain the same 2–10 points in matching finger order, each point contains exactly integer `x`/`y` in 0–65535, and `durationMs` is an integer from 200 to 5000. The helper checks the emulator discovery record against the selected ADB AVD, connects to loopback using its private token, schedules interpolated touch frames, then sends zero pressure for its own touch IDs. `release: "scheduled"` is a gRPC scheduling receipt, not proof of device UI success. Inspect the receipt, then re-observe the app. It does not change the emulator's authentication mode, grant permissions, support physical devices, JWT-only endpoints, unauthenticated endpoints or non-macOS discovery. If the gesture or release is uncertain, preserve its run and inspect the device rather than retrying; abrupt process termination can prevent the release request. Google documents the [emulator gRPC interface](https://developer.android.com/studio/run/emulator-console) and its [touch protocol](https://android.googlesource.com/platform/external/qemu/+/refs/heads/emu-master-dev/android/android-grpc/emulator_controller.proto).
