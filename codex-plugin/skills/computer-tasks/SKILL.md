# Plan, track and recover computer tasks

Use the [core calling contract](../cloud-connection/references/calls.md) once per task and target version. For interrupted or uncertain execution, read [recovery.md](../cloud-connection/references/recovery.md); original-ID recovery need not wait for skill reloading. For plans and handoffs read [context.md](references/context.md) and, when setting or changing primary storage, [planning.md](../cloud-connection/references/planning.md). For independent work on one or several machines, follow the shared [concurrency reference](references/concurrency.md).

## Plans, progress and handoff

- When an answer or action is required from the user, record the blocker and affected dependencies, then continue independent authorized work. Never assume an essential answer or approval. Before yielding with unresolved blockers, organize the visible context and confirmed decisions, completed work, verification, remaining work and original IDs; consolidate all unanswered questions and required user actions in the final response. Save the summary in the appropriate task record when authorized and applicable, and report any save gap. Follow higher-priority host and user instructions about asking or waiting.
- The tasks catalog includes `project_journal(action=open)`, `project_journal(action=latest)`, `project_journal(action=record_compaction)` and `read_artifact`. This is a discovery/UI category only: other Skills, including App and mobile workflows, may use `read_artifact` with the same binding and permissions.
- `task_state(list)` reads the original machine's bounded client-local status list for this binding, session and caller, including tool names, start/update times and last observed states. `set` and `clear` manage caller-reported entries, not processes or approvals. `includeLatestOutput=true` fetches a bounded current log tail for at most eight owned run references without persisting that line in the status list; it may contain sensitive content. Check original run/call/recording receipts and an incomplete or stale list before relying on it. Before task completion, stop any recording that was requested for this task and confirm the resulting artifact; if it is unconfirmed, preserve its original identifiers and report that state.
- Answer simple questions directly unless the user explicitly requests a record. For authorized project work requiring a record, read project instructions first; use `project_journal(action=latest)` when resuming the latest unfinished task, otherwise open the project's `.remopilot` journal. Read its lessons, preserve the original task session, and promptly update `PROCESS.md` with concrete progress, blockers and original execution IDs before waiting or handing off. Follow [project-journal.md](../cloud-connection/references/project-journal.md), keep `base.info` current, write `summary.md` on verified completion, and personally organize and save a visible-context summary when requested or before a planned handoff or compaction. A machine-only task has no invented project.
- The host decides when a durable plan is needed and saves it with `task_update(checkpoint)`, updating it as appropriate to the task and project instructions. It is separate from project files, and caller-local notes are not the only recovery copy. Every scoped checkpoint needs explicit bindingIds and state.workspaceMap, including primaryBindingId and one role per binding. Verify actual returned storage; a local relay SQLite may be on a different machine.
- Include the task sessionId and expectedRevision. On REVISION_CONFLICT, resume and merge before writing. Preserve actual original IDs in runs and sourceHandoffId when continuing a snapshot. Save visible goals, decisions, verified results, unresolved issues and next steps, not private reasoning, credentials or full logs. Recover an uncertain save with identical arguments and requestKey.
- Resume with `task_query(session_resume)` and inspect blockingReview, nextAction, newer events and original runs before continuing. Use `task_query(restore, arguments={handoffId})` for a requested immutable snapshot; `task_update(session_append)` explicitly records requirements that did not pass through execution tools. Neither saves the entire host chat automatically nor grants permission to replay.
- Report the session/task/handoff IDs, actual storage machine and reference, original bindings and real project paths needed for recovery. A taskUrl opens the authenticated latest-task page; a handoff is a snapshot. Cloud restoration requires its primary machine online; if unavailable, report the gap while continuing independent original-ID recovery. Restore temporary access only under the user's authorization.

## Independent work and shared resources

Map every action to its own machine and binding. A task session can retain multiple targets; the caller coordinates them without a separate coordination skill. Inspect actual scripts, hooks, files, outputs, caches, ports, Git and devices before parallel dispatch; declare real workspace, resource or machine conflicts. Dispatch independent work concurrently where supported, retain separate request and run/call IDs, and start dependents only after the required executions and artifacts are verified. Failures block only their dependents; accepted or uncertain calls are recovered rather than replayed. The agent executes tools, not model subagents or an automatic dependency graph.

## Observe and recover execution

Retain sessionId, original bindingId, requestKey/requestId and actual runId/callId for every action. Start long work with the background mode advertised by its schema; observation and execution budgets are separate. Observe independent runs separately and continue unrelated authorized work.

An agent-owned monitor checks known active background executions about every five seconds while the agent and original access are available. A newly confirmed ending may appear once in `note` on a later tool response for the same session, including task, status, finish time, retained log line count and original IDs. A null time or line count means unavailable; truncated logs are marked. Review the original request and run/call before dependent work. The note is a delivery attempt, not proof the host consumed it; no later call means no automatic host turn, and an offline machine or unconfirmed execution can delay the note.

1. Read task_query(result) by the original binding and requestId, or the original requestKey if the first response was lost. A relay receipt marked complete only means its handler output is readable.
2. Inspect subjectExecution when present, then actual output, status, terminal/unfinished/closure evidence, exit code and required verification. A missing field is unknown, not false. The cloud does not supply the local relay's complete execution/occupancy projection; do not treat a cloud receipt as proof that the machine released resources.
3. Continue through manage_run with the original runId, or manage_call with the original callId. A finished observation query does not finish its subject. For current_run_snapshot, retain originalResult as history and inspect the current result; large results may require an artifact read.
4. Follow continuation/next and retry timing instead of busy polling. Each observation is a new query with its own request key; it keeps the queried execution ID unchanged. Missing records or unconfirmed state do not permit a replacement execution.
5. On later turns, resume the session and review blockingReview/nextAction. If a detached task ended unsuccessfully, inspect its original evidence before continuing dependent work. Once terminal error is confirmed, review it instead of polling indefinitely.

manage_run includes read-only queries and the mutating extend action; its overall tool annotation is therefore mutating. Ordinary status/log/wait remains observation. Extending the deadline and cancel_run affect execution and must follow the user's requested scope. A cancellation rejection proves only that cancellation was not dispatched; observe the original run to establish its state.

task_update(input) records requirements for later planning. It does not send stdin, change a command or restart it. Read task_query(events) incrementally before planning dependent actions. Read logs with byteOffset/tail and follow returned offsets; use search_log for focused evidence.

For WORKSPACE_BUSY, follow blocker/next and verify the holder's original terminal state and release before retrying the undispatched action. For binding or route errors, follow returned original targets; do not guess a project, clear locks or change keys to bypass them. Maintenance or generation changes preserve original execution ownership. Record uncertain state as “异常：执行状态待确认”, keeping raw uncertainty in evidence.

Completion requires actual execution and requested outcome evidence. Host animations, delivery acknowledgements, an idle list or a stored summary do not establish it. Preserve incomplete records and report the gap; deleting state cannot turn an uncertain task into a completed one.
